# ファイル注釈プロバイダ — 外部のコメントを生テキストの横に出す口

## 何をしたいか

別のシステム（レビューツール、クライアントのフィードバック用 DB）が持っているコメントを、Files ペインで
開いたファイルの該当行の横に出したい。読むだけでなく、その場で返信し、対応済みにし、隣のターミナルの
エージェントに「このコメントに対応して」と渡せるようにする。

きっかけは、原稿（Markdown）に付いたクライアントコメントを Cursor 拡張で表示している別プロジェクト。
同じことを MulmoTerminal でやろうとすると、既存の拡張点では足りなかった:

- **コレクションのカスタムビュー**は sandbox の iframe で、自分のコレクションのデータ以外に通信できない。
  返信は `startChat` 経由でエージェントに頼むことになり、1 返信ごとにエージェントが 1 ターン動く。
- **GUI プラグイン**は `plugins/plugins.json` とフロントの静的 import に焼き込まれていて、足すには
  本体のビルドが要る。しかも Canvas に出るもので、エディタの行には紐づかない。

## 決めたこと

### 1. 口は「宣言されたコマンド」にする

プロバイダはユーザーが設定に書くコマンド。stdin に JSON の依頼を 1 つ、stdout に JSON の答えを 1 つ。
本体はコメントの出どころを一切知らない。

HTTP エンドポイントや MCP クライアントにしなかった理由:

- HTTP だと、相手の API の形（認証ヘッダ、ページング、エラーの形）を本体が知るか、相手側に本体専用の
  エンドポイントを生やしてもらうかになる。どちらも「本体は出どころを知らない」に反する。
- MCP は道具の呼び出しであって、返ってくるのは人間向けの文章。行番号つきの構造化データを毎回
  安定して取り出す契約にならない。OAuth のクライアントを本体が持つことにもなる。
- コマンドなら、認証もアンカーの解決も相手側のコードをそのまま使える（import できる）。

### 2. 宣言はグローバル設定だけ

`~/.mulmoterminal/config.json` の `annotationProviders`。プロジェクトの `.mulmoterminal.json` には置かない。

このコマンドは**ファイルを開いただけで走る**。プロジェクトの設定はクローンと一緒に届くので、そこに
置けると「リポジトリを開いたら他人のコマンドが動く」になる。ヘッダーボタンの `run: "shell"` が
プロジェクト設定に置けるのは、押すまで走らないから。

### 3. argv で実行する。シェルは通さない

カスタムエージェントと同じ規則・同じトークナイザ（`tokenizeCommandLine`）。`~` も `$HOME` も展開しない。

### 4. 行に置くのはプロバイダの仕事

ワイヤに載るのは 1 始まりの行番号と `placement`（`exact` / `moved` / `estimated` / `unplaced`）だけ。
オフセットも版 ID も載せない。

元のシステムはたいてい「ある版のテキスト中のオフセット + 引用文」でコメントを持っている。それを
いまのテキストに当て直すには版の履歴が要り、本体はそれを持たない。だからプロバイダに `content`
（いまディスクにあるテキスト）を渡して、行にして返してもらう。分からなければ `unplaced` と言って
もらう。間違った行に出るより、どこにも出ないほうがまし。

エディタは受け取った行を、読み手のタイプに合わせて運ぶだけ（変更マークの gutter と同じやり方）。

### 5. 出すのは生テキストの横だけ

プレビューは別の文書で、コメントを掛ける「行」がない。プレビュー中はエディタごと隠れているので、
パネルも出さない。side-by-side のときはエディタが見えているので出る。

### 6. エージェントへの受け渡しは「入力欄に入れるだけ」

パネルの「エージェントに頼む」は、ファイルの参照・プロバイダの `instructions`・各スレッド（ID つき）を
並べた依頼文を、隣のセルの入力欄に入れる。送信はしない。`@` ボタン（#2575）と同じ経路・同じ規則で、
未保存の編集は先に保存する（エージェントが読むのはディスク上のファイルなので）。

エージェント側から返信・解決する手段は本体は用意しない。相手のシステムの MCP サーバを `.mcp.json` に
登録しておけば足りる。スレッド ID を依頼文に入れているのはそのため。

### 7. 1 つのプロバイダの失敗でファイルは止めない

一覧（GET）は、プロバイダが落ちても 200 で、そのプロバイダの `error` を他のプロバイダのスレッドと
並べて返す。返信・解決（POST）は相手が 1 つなので、失敗はそのまま 502。

## 触ったところ

| | |
|---|---|
| `common/fileAnnotations.ts` | 契約。設定エントリ・ワイヤの型と、信用しない前提の読み取り |
| `server/files/annotation-provider.ts` | コマンドの実行（タイムアウト 20 秒、出力 8MB まで） |
| `server/files/files-annotations.ts` | `GET` / `POST /api/files/browse/annotations` |
| `src/components/cmAnnotationGutter.ts` | gutter の印と行の色。タイプに追従 |
| `src/composables/useFileAnnotations.ts` | 読み込み・返信・解決 |
| `src/components/FileAnnotationsPanel.vue` | スレッドのパネル |
| `samples/annotation-provider/` | 1 ファイルで完結する見本 |

`FilesPane.vue` は行数の上限（600）ちょうどだったので、競合バナーを `FilesConflictBanner.vue` に
切り出して場所を作った。動きは変えていない。

## やっていないこと

- **新しいコメントを作る操作。** 一覧・返信・解決だけ。
- **Settings の UI。** エントリはサーバが実行するコマンドなので、手かスキルで書く。
- **自分の返信の編集・削除。** 元のシステムにはあるが、契約を小さく始める。
- **提案（差分つきの修正案）の表示と採否。** コメントとは別の物なので別の口になる。
- **プロバイダ結果のキャッシュ。** ファイルを開くたび、ディスク上で変わるたびに 1 回走る。
